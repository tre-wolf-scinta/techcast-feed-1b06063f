Trigger Best Practices and the Handler Pattern

A trigger passes every unit test, goes live, and the first data load of the morning fails with the error too many SOQL queries, one hundred and one. Nothing changed in the code. So what did the data load do that the tests never did?

Think of a cashier at a checkout line. One cashier walks to the back room to look up the price of every single item in your cart, one trip per item. Another cashier takes the whole list, makes one trip, and comes back with every price at once. A query inside a loop is the first cashier. A single query over a collection is the second. The platform gives you a strict trip budget per transaction, and the exam wants you to know how to stay inside it.

Here is the scenario. Maya writes an after update trigger on Opportunity. For each opportunity in the trigger's new list, she queries its parent Account, increments a counter field, and updates that account. It works perfectly in the sandbox, because she tests with one record. Then Data Loader pushes two hundred opportunities in one batch, and triggers process up to two hundred records at a time. That is two hundred queries and two hundred update statements in one transaction. The limit is one hundred SOQL queries and one hundred and fifty DML statements per synchronous transaction, so the whole batch rolls back on query one hundred and one.

The fix is called bulkification. Maya loops over the new records once and collects every account Id into a set. She runs one query with an IN clause and loads the results into a map keyed by Id. She loops again, in memory this time, bumps each counter, and adds the changed account to a list. Then one update statement sends the list. One query, one DML statement, whether the batch holds one record or two hundred. When the exam shows you trigger code and asks what is wrong, look for a query or a DML keyword sitting inside a for loop first. That is the answer most of the time.

Now, where does that logic live? Not in the trigger. The trigger stays a thin dispatcher. It checks the context variables, whether it is before or after and which operation fired, and calls the matching method on a handler class. This is the trigger handler pattern, and it comes paired with a rule of one trigger per object. The reason is simple. When several triggers exist on the same object for the same event, Salesforce does not guarantee the order they run in, so you cannot reason about the result. One trigger, one handler, order under your control.

There is one more trap. Maya's handler updates accounts. A separate account trigger updates related opportunities. That fires Maya's opportunity trigger again, which updates accounts again, round and round until a limit breaks the loop. The guard is a static variable on the handler class, because static state lives for exactly one transaction. The simple version is a static boolean flag set to true on first entry. The better version is a static set of processed record Ids. Skip any record already in the set, add the rest, and continue. The set is preferred because a plain flag can wrongly skip a later batch of brand new records in the same transaction, while the set only blocks the exact records that already ran.

So the rule to remember. One trigger per object, logic in a handler, one query and one DML per transaction no matter the batch size, and a static set of Ids to stop the trigger from calling itself.
