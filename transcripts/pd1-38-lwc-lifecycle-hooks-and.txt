LWC Lifecycle Hooks and Reactivity

A Lightning Web Component has a button. Maya clicks it, the handler runs, the data clearly changes, and the screen does nothing. The Platform Developer One exam loves this setup, then asks which lifecycle hook or decorator is missing. To answer it you need two things: the order the hooks fire in, and the exact rule for what counts as a change.

Think of the framework as a doorman at an apartment building. He notices every time a tenant moves in or out of a unit, but he has no idea when someone rearranges the furniture inside. Each field on your component is a unit, and the framework watches the door, not the furniture.

Say Maya's component shows a contact's shipping address. The constructor runs first. It must call the parent constructor with super before anything else, and at that point the component is not in the page, so there is no DOM to touch and its public properties have not been assigned yet. Then connectedCallback fires when the component is inserted into the page. It runs parent first, then children, and the component's own child elements still do not exist, so this is the place to load data or add a window listener, not to query the template. After every render, renderedCallback fires, children before parents. It is the one safe place to read the rendered DOM, but it can fire many times, so Maya guards it with a boolean flag. Setting a reactive field inside it without a guard rerenders, which fires it again, forever. When the component is removed, disconnectedCallback fires, and that is where she removes the window listener. Last, errorCallback receives an error object and a stack string whenever a child component throws inside one of its own lifecycle hooks. It is the error boundary for everything below it.

Now the bug. Maya stores the address as an object field, and her template prints address dot street. Her click handler sets this dot address dot street to the new value. Nothing repaints. Why? Every field in a Lightning Web Component is reactive by default, but reactive means the framework rerenders when the field itself is assigned, and only if the template uses it. She rearranged the furniture, and the doorman saw nothing. There are two fixes. Reassign the whole field with a new object, for example spreading the old address and overriding street, so the door actually opens. Or decorate the field with at track, which tells the framework to observe the object's internals, including nested properties and array elements. Primitives like strings and numbers never need at track, and at api properties are reactive on their own.

So when the exam says the component does not update, ask two questions: was the field reassigned or only mutated, and was the DOM touched before renderedCallback. Assignment rerenders, mutation needs at track, and the DOM exists only after render.
