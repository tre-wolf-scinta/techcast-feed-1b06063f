Custom Fields and Record Types for PD1

Priya is building a custom Invoice object for an online store, and the requirements look simple. Every invoice needs a number nobody types by hand, a status chosen from a fixed list, a notes field that can hold a page of text, and a paid flag. Which field type satisfies each one with the least customization? That is exactly the kind of question the exam asks.

Think of a paper form from a print shop. Each box has a fixed number of character cells, some questions are tick boxes instead of blank lines, and the serial number in the corner is stamped before the form ever reaches you. A custom object is that form, and every field type is a decision about the shape of one box.

Start with the invoice number. Priya could make it a text field and ask people to type the number themselves, but someone will skip a value or enter a duplicate. Instead she creates a field with a display format of the letters INV followed by four digits in braces, and Salesforce stamps the next value on every new record. That is an Auto Number field. It is read-only, it increments on its own, and it can even replace the standard Name field on the object.

Now the status. A text field accepts anything, so one person types Paid, another types it in capitals, and the report splits in two. A picklist gives a fixed list of values, and marking it restricted blocks the API from inserting anything outside that list. For the notes, a plain Text field tops out at 255 characters, and a Text Area is also 255 but spans multiple lines. Priya needs a Long Text Area, which defaults to 32,768 characters and can go up to 131,072. For the invoice total she picks Number or Currency and sets the precision, up to 18 digits in total, split between the digits before and after the decimal point. And the paid flag is a Checkbox. A checkbox always has a default of checked or unchecked, it can never be blank, and it cannot be marked required.

Then the complication arrives. Sales wants statuses of Draft and Sent, while finance wants Paid, Disputed, and Written Off, on a different page layout. Priya could clone the object or pile on validation rules, but the smaller tool is a Record Type. A record type controls three things: which picklist values a user sees, which page layout each profile gets, and on Lead, Opportunity, Case, and Solution, which business process the record follows. It does not control field-level security and it does not add fields. Priya creates two record types, assigns each one a layout and a trimmed picklist, and the same object now serves both teams.

So the rule for the exam: match the field type to the shape of the data (Auto Number for system-stamped values, a picklist for fixed lists, Long Text Area past 255 characters, a Checkbox with a default), and reach for record types when different users need different picklist values, layouts, or business processes on one object.
