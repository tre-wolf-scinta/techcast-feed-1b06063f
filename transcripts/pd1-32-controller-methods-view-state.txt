View State and the Visualforce Page Lifecycle

Sam builds a Visualforce page with a search box and a Search button. He types Acme, clicks the button, and the results come back empty. The search term never reached the controller. Why not?

Think of the page as a backpack the browser carries to the server and back. Every time Sam clicks a button, the browser hands over the backpack, the server unpacks it, does the work, repacks it, and hands it back. In Visualforce that backpack is called view state. It is an encrypted hidden field inside the page's form, and it holds the values of your controller's instance variables plus the state of the component tree. Sam's page has an input bound to a searchTerm property and a command button bound to an action method called runSearch. The controller also holds a list of accounts to display.

On the first visit the request is a plain get. The constructor runs, the getters run to fill in every expression on the page, the page renders, and the server packs the view state. Now Sam clicks Search. That is a postback. The server decrypts the view state and rebuilds the controller object exactly as it was. Then it calls the setters for every bound input, so setSearchTerm receives Acme. Then it runs the action method. Then it re-renders, calling the getters again, and writes a fresh view state. So where did Sam's value go? His input tag sat in a second form, separate from the form holding the Search button. Only the fields in the form that gets submitted are posted back, so the setter never ran. Two more classic reasons a value fails to persist: a getter that computes a value on the fly but never stores it, and a getter with side effects. Getters can be called more than once per render, in no guaranteed order, so they should only read. The action method itself returns a PageReference. Return null and the same page re-renders with the controller's current state. Return a new PageReference and the user navigates away, and if that is a redirect to a different page, the view state is discarded and a fresh controller is built.

Sam moves the input into the same form as the button, and the search works. Then he loads five thousand accounts with twenty fields each into his list, and the page fails with a view state error. The limit is 170 kilobytes, and every non-transient instance variable gets serialized into the backpack on every trip. The fix is the transient keyword. Mark the list transient and it is left out of view state, but that means it is gone on the next postback, so the action method has to query it again. Transient is also the right choice for sensitive data, because view state is encrypted but still travels to the browser. Beyond that, query only the fields the page shows, keep a single form, and keep components that do not need a postback outside it.

On a postback the server rebuilds the controller from view state, runs the setters, runs the action method, then runs the getters, so keep each input in the same form as its button, store only what must survive in non-transient variables, and mark everything else transient to stay under 170 kilobytes.
