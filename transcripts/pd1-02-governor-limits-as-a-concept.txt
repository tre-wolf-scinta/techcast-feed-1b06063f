Governor Limits: One Budget Per Transaction

Why does a trigger that works perfectly on one record fall over when a data loader pushes in two hundred? The answer is governor limits, and the Platform Developer I exam wants you to spot the line that trips one before the code ever runs.

Think of a shared kitchen in an apartment building. Everyone gets the same stove for a fixed slot, and if you leave the burner on past your time, the building cuts the gas so nobody's dinner can monopolize it. Salesforce is that building. Your org shares servers with thousands of other orgs, so every transaction gets a fixed budget of queries, writes, memory, and processor time, and when you blow the budget the platform kills the transaction and rolls it back.

Maya writes a trigger on Opportunity. For each opportunity, she queries the parent Account to read its region, then updates a counter field on that account. She inserts one opportunity from the user interface and it works. Then a data loader inserts two hundred opportunities in one batch. The trigger fires once with all two hundred records, the loop runs two hundred times, and each pass issues a query. On pass one hundred and one, Salesforce throws a limit exception that says too many SOQL queries. You can't catch that exception. The whole transaction rolls back, and all two hundred rows fail.

Now, the budget is counted per transaction, not per user and not per org. A transaction is everything from the moment the insert starts until the last trigger, flow, and workflow rule has finished. If a second trigger on Account also runs queries, those count against the same pool. For synchronous Apex, the headline numbers are one hundred SOQL queries, one hundred fifty DML statements, fifty thousand rows returned by queries in total, ten thousand records processed by DML in total, six megabytes of heap, and ten seconds of CPU time. Asynchronous Apex, meaning future methods, queueable jobs, batch jobs, and scheduled jobs, gets a bigger room on some of those: two hundred queries, twelve megabytes of heap, and sixty seconds of CPU. The DML limits stay the same. CPU time counts your Apex, not time spent waiting on the database or a callout.

So the fix is to spend the same budget whether one record or two hundred arrive. Maya collects the account IDs into a set, runs one query, puts the results in a map keyed by ID, and issues one update with the whole list. One query and one DML statement, every time. That habit is called bulkification, and it's the single most tested idea on the exam.

The exam will hand you code and ask which limit it hits. A query inside a loop over two hundred records dies at query one hundred and one. An update inside that same loop dies at DML statement one hundred fifty-one. A single query that returns sixty thousand contacts breaks the fifty thousand row ceiling even though it was only one query. A loop that keeps appending to a giant string or list blows the six megabyte heap. And if you need to check your remaining budget at runtime, the Limits class has a method for every one of these counters.

Every transaction gets one shared budget, so write code that costs the same for one record as it does for two hundred.
