Debug Logs and Trace Flags

Sam's opportunity trigger throws a too many SOQL queries error in production, but only when the nightly integration loads records under his user, and you can't reproduce it in a sandbox. How do you see what Apex actually did on his transaction, without breakpoints and without logging every user in the org?

Think of a dashcam you can clip to one driver. You pick who it follows, you set the window it records in, and you pick the resolution so a day of footage doesn't fill the card. On the platform, the who and when is a trace flag, and the resolution knob is a debug level.

In Setup, under Debug Logs, Maya creates a trace flag. The traced entity can be a user, an Apex class or trigger, or the Automated Process user that runs scheduled and automated work. She picks Sam, sets a start time and an expiration time, and attaches a debug level. A debug level is a saved record with one setting per category: Apex Code, Database, Workflow, Validation, Callouts, System, Apex Profiling, and a few more. Each category gets one of eight levels, from NONE and ERROR up through WARN, INFO, DEBUG, FINE, FINER, and FINEST, and finer means more lines. She sets Apex Code to DEBUG, Database and Apex Profiling to INFO, and everything else to ERROR. One subtlety the exam likes: a trace flag on a class overrides the user's levels for that class only, but it doesn't create logs by itself. A user or automated process trace flag still has to be active when the code runs.

The integration runs, and a log appears. USER_DEBUG lines are Maya's own System.debug calls, each tagged with a line number and the message, visible because Apex Code is at DEBUG or finer. SOQL_EXECUTE_BEGIN shows each query as it fires, with the query text, and the matching SOQL_EXECUTE_END shows how many rows came back. She sees the same query firing two hundred times, once per record. At the bottom, the cumulative limit usage block lists each governor limit against its ceiling: one hundred SOQL queries out of one hundred, with the exception right after it. The query inside the loop is the bug.

It's tempting to set everything to FINEST next time. Don't. A single log is capped at 20 megabytes, and past that Salesforce trims older lines from anywhere in the file, so the evidence you wanted can vanish. And if your org generates more than 1,000 megabytes of logs in a 15 minute window, your trace flags are disabled and you wait 15 minutes to turn them back on. When a log can't tell you what a variable held, open the Developer Console and set a checkpoint on a line. When execution reaches it, the platform takes a heap snapshot of the objects in memory and keeps going, because Apex never pauses for a debugger.

The trace flag says who and when, the debug level says how much per category, and the log's debug, query, and limit lines tell you where the transaction went wrong.
