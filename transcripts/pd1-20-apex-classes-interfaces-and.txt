Apex Interfaces, Classes, and Sharing Keywords

Why can the Salesforce platform run your batch class at two in the morning when it has never seen your code before? And why does that same class sometimes return records the running user is not allowed to see?

Priya is writing a nightly job to close out fifty thousand stale opportunities. Her first draft is a plain class with a method named cleanUp. It compiles, but the batch engine has no idea what cleanUp is. Think of a wall outlet. It does not care whether you plug in a lamp or a laptop charger. It only cares that the plug has the right shape. An Apex interface is the plug shape: a list of method signatures with no bodies, and the platform is the outlet that will call them.

So Priya declares her class as implementing Database dot Batchable, and now the compiler forces her to write three methods. Start returns the records to process, execute handles each chunk, and finish runs once at the end. The batch engine calls those three by name on any class that implements the interface, and it needs to know nothing else about her code. This is called a contract. Schedulable is the same idea with a single execute method the scheduler fires on a cron expression. Queueable has one execute method the async queue calls. Comparable asks for a compareTo method, which is how List dot sort knows how to order your own objects.

An interface gives you a contract with no shared code. When you want shared code too, you use classes. A class marked virtual can be extended, and any method marked virtual can be replaced in a subclass using the override keyword. An abstract class goes further: it can declare abstract methods with no body that every subclass must implement, while still carrying concrete helpers they all inherit. Priya moves her logging into an abstract CleanupJob class, marks the record-picking method abstract, and each nightly job extends it. Nobody can instantiate CleanupJob directly, only its concrete children.

Now the second question. A support rep kicks off a related job from a Lightning page, and it reads opportunities that rep cannot see. The fix is a sharing keyword on the class declaration. With sharing enforces the running user's record-level sharing rules on every query in that class. Without sharing ignores them. Inherited sharing runs with sharing when the class is the entry point, and otherwise takes whatever mode the caller is already in. Two exam traps here. First, the keyword that applies is the one on the class where the method is defined, not the class that called it, so a with sharing controller that calls a without sharing helper gets unfiltered results back. Second, sharing keywords only govern record sharing. Object permissions and field-level security are a separate check you still make in code.

An interface is a contract the platform can call without knowing your code, a class is where shared behavior lives, and the sharing keyword that counts is the one on the class that actually runs the query.
